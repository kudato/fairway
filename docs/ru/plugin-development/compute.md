# Вычисления

`fairway-compute` выполняет синхронные вычисления в общем пуле потоков
и возвращает результат в асинхронный код. Он подходит для обработки данных
в памяти: сортировки, анализа текста, построения индексов и других вычислений.

## Быстрый старт

`run` принимает замыкание с вычислением. `.await` дожидается свободного места
в пуле, затем результата работы, не блокируя ожидающий поток.

```rust
use fairway_compute as compute;

async fn sorted(mut values: Vec<u64>) -> Vec<u64> {
    compute::run(move || {
        values.sort_unstable();
        values
    })
    .await
}
```

`move` передаёт входные данные замыканию. Результат возвращается напрямую:
дополнительной обёртки вокруг `Vec<u64>` нет.

## Пример обработки текста

В этом примере `run` получает уже прочитанный текст и возвращает число слов.

```rust
use std::{io, path::Path};

use fairway_compute as compute;
use fairway_fs as fs;

async fn count_words(path: &Path) -> io::Result<usize> {
    let text: String = fs::read(path).await?;
    let count = compute::run(move || text.split_whitespace().count()).await;
    Ok(count)
}
```

## Возврат ошибки

Замыкание может вернуть `Result<T, E>`. `run` передаёт его вызывающему коду
без изменения, поэтому после `.await` можно использовать обычный `?`.

```rust
use std::num::ParseIntError;

use fairway_compute as compute;

async fn parse_numbers(text: String) -> Result<Vec<u64>, ParseIntError> {
    compute::run(move || text.lines().map(str::parse::<u64>).collect()).await
}
```

## Параллельные вычисления

Несколько одновременно ожидаемых вызовов `run` могут выполняться параллельно
в пределах общего лимита. Последовательные вызовы с `.await` выполняют работу
по очереди.

Один вызов `run` переносит замыкание на поток пула. Сам алгоритм автоматически
не распараллеливается. Для этого внутри замыкания можно использовать
параллельные итераторы или `join` из [Rayon](https://docs.rs/rayon/latest/rayon/struct.ThreadPool.html):
они выполняют подзадачи в том же пуле.

```rust
use fairway_compute as compute;
use rayon::prelude::*;

async fn parallel_sorted(mut values: Vec<u64>) -> Vec<u64> {
    compute::run(move || {
        values.par_sort_unstable();
        values
    })
    .await
}
```

Для этого примера плагину нужна прямая зависимость от `rayon`.
Подзадачи должны завершиться до возврата из замыкания, как у параллельных
итераторов и `rayon::join`. Отдельно запущенные фоновые задачи `run` не отслеживает.

## API

### run

- `async fn run<T>(work: impl FnOnce() -> T + Send + 'static) -> T`
  — выполняет `work` в общем вычислительном пуле и возвращает его результат.
  Требует `T: Send + 'static`.

Замыкание синхронное и возвращает готовый результат. Если оно возвращает
`async`-блок, пул только создаёт future и не выполняет её.

Вычислительный пул предназначен для обработки данных в памяти.
Ввод-вывод и ожидание внешних операций выполняются вне пула.

`Send` позволяет передать замыкание и результат между потоками. `'static`
запрещает заимствования с меньшим временем жизни, но не требует хранить данные
до конца процесса. Обычно замыканию передают принадлежащие ему значения
через `move`; для совместного владения можно использовать `Arc`.
Сам по себе `move` не продлевает время жизни захваченных ссылок.

Если результат — `Result<T, E>`, оба типа должны быть `Send + 'static`.
Ограничений `Sync` и `std::error::Error` у `run` нет.
Возвращаемая future реализует `Send`.

Создание future не запускает работу. Она передаётся в пул, когда future
опрашивается и получает свободное место. Если работа передана, `work`
вызывается один раз. Порядок запуска и завершения независимых вызовов
не гарантируется.

### Пул и ограничение нагрузки

Пул на Rayon общий для всех вызовов `compute::run` из крейтов ядра и плагинов.
Работа всегда выполняется в пуле независимо от размера входных данных.

Пул создаётся автоматически при первом опросе future `run` и живёт до конца
процесса. Число потоков определяется один раз через
`std::thread::available_parallelism()`; если определить его нельзя,
используется один поток. Настройка потоков Tokio этот лимит не меняет.

Число переданных в пул незавершённых вызовов `run` ограничено числом потоков.
Остальные вызовы асинхронно ждут свободного места до передачи работы в Rayon.
Лимит относится к вызовам `run`, а подзадачи Rayon используют те же потоки.
Ожидающие вызовы сохраняют свои входные данные, поэтому этот лимит не ограничивает
общий расход памяти и число созданных вызывающим кодом future.

Вычисления не занимают рабочие потоки Tokio и его пул блокирующего ввода-вывода.
`run` не создаёт асинхронный runtime. Крейт можно использовать в тестах и других
приложениях без запуска `fairway`; пул не привязан к конкретному runtime.
Ожидание использует [примитивы Tokio, совместимые с разными исполнителями](https://docs.rs/tokio/latest/tokio/sync/index.html#runtime-compatibility).

Завершение runtime не останавливает уже переданные в пул вычисления.
Чтобы они завершились до выхода из приложения, вызывающий код должен
дождаться соответствующих `run`.

Внутри работы вызывайте вложенные вычисления синхронно или через Rayon.
Блокирующее ожидание вложенного `compute::run` может привести к взаимной
блокировке: внешняя работа удерживает место в пуле, которое требуется вложенной.

### Отмена

Отмена означает уничтожение future, возвращённой `run`:

- До передачи работы в пул замыкание не вызывается; захваченные им данные
  освобождаются вместе с future.
- После передачи в пул работа выполняется, даже если она ещё не успела начаться.
  Отмена ожидания её не прерывает. Место остаётся занятым до завершения работы
  и освобождения оставшихся у неё ресурсов.
- Если ожидание отменено, результат завершившейся работы отбрасывается.

Таймаут ожидания действует по тем же правилам: уже переданное в пул вычисление
продолжает работу. Для досрочного завершения длительный алгоритм должен сам
проверять переданный ему сигнал отмены и возвращать результат.

### Ошибки и паники

`run` возвращает именно результат замыкания. Собственного типа ошибки
или дополнительного `Result` у него нет.

При `panic = "unwind"` паника из `work` переносится в ожидающий код с исходной
причиной. Пул после неё остаётся пригодным для следующих вызовов.
Если ожидание уже отменено, передавать панику некому; место в пуле освобождается
после завершения работы. При `panic = "abort"` паника завершает процесс.

Невозможность создать вычислительный пул приводит к панике при его инициализации.
